# Ресторан: админка, официант, кассир, кухня

Ресторанная версия «Кассы и склада». Тот же Laravel-проект, та же база и тот же вход по PIN, плюс четыре
приложения для ресторана, платёжный терминал кассы и синхронизация с облачным сервером. Склад, приход,
инвентаризация и прогнозы кассы остаются на месте: ресторан ведёт в них склад продуктов.

| Приложение | Адрес | Кто входит | Устройство |
|---|---|---|---|
| Админка | `/admin` | владелец, администратор | компьютер, планшет |
| Официант | `/waiter` | официант (и администратор) | телефон (основной размер 390–430 px), планшет |
| Кассир | `/cashier` | кассир (и администратор) | планшет или компьютер на кассе, телефон |
| Кухня (KDS) | `/kitchen` | повар (и администратор) | настенный монитор на кухне — только просмотр |
| Касса и склад | `/kassa/` | владелец, администратор, продавец | телефон, планшет |

Варианты развёртывания из одной ветки — [чистая установка](#21-чистая-установка) (пусто, первый запуск через
мастер) и [демонстрационная](#22-демонстрационная-установка) (данные только из `restaurant:demo`).

Один магазин кассы (`kassa_stores`) — один ресторан. Все данные хранят `store_id`, рестораны изолированы
(глобальный scope `StoreScope`), владелец может вести несколько ресторанов и переключаться между ними.

## 1. Архитектура

```
 телефоны официантов ─┐                                                   ┌─► принтер кухни (ESC/POS, порт 9100)
 касса (кассир) ──────┤                                                   │
 экран кухни (KDS) ───┼── Wi-Fi ресторана ──► ЛОКАЛЬНЫЙ СЕРВЕР ───────────┤
 админка ─────────────┘                       (DEPLOY_MODE=local)         └─► банковский терминал кассы (адрес:порт)
                                              Laravel + SQLite, работает без интернета
                                                         │  раз в день, HTTPS + sync-токен
                                                         ▼
                                               ОНЛАЙН-СЕРВЕР (DEPLOY_MODE=online)
                                               сводная админка и отчёты, меню и настройки
```

### 1.1. Четыре приложения — четыре PWA

Код — без сборки и внешних библиотек, поэтому всё работает в локальной сети без интернета:

| Что | Где |
|---|---|
| Страницы, манифесты, service worker | `routes/restaurant.php`, `app/Http/Controllers/Restaurant/PageController.php` |
| Layout каждого приложения | `resources/views/restaurant/layouts/{admin,waiter,cashier,kitchen}.blade.php` |
| Клиент | `public/restaurant/common.js` (общее), `floor.js` (зал — общий модуль официанта и кассира) + `admin.js`, `waiter.js`, `cashier.js`, `kitchen.js`, `restaurant.css`, иконки |
| API | `/api/restaurant/*` (`routes/api.php`), контроллеры `app/Http/Controllers/Api/Restaurant/` |

У каждого приложения свой адрес, свой layout и своя конфигурация PWA: манифест `/{app}/manifest.webmanifest`
с собственными `id`, `start_url`, `scope`, иконкой и цветом, и service worker `/{app}/sw.js` с областью `/{app}`
(заголовок `Service-Worker-Allowed`). Поэтому на одно устройство их можно поставить как отдельные приложения.
Кухня открывается в полноэкранном режиме (`display: fullscreen`, ландшафт). Service worker хранит оболочку
приложения: если Wi-Fi на секунду пропал, приложение откроется и покажет «нет связи», а не пустой экран.

**Анимации** — во всех приложениях сдержанные, в духе белой минималистичной кухни: переход между экранами —
мягкое появление со сдвигом (≈220 мс), новый заказ на кухне проявляется на своём месте, остальные карточки плавно
доезжают (FLIP — без скачков вёрстки), карточка, сменившая статус, переезжает в свою колонку; добавленное в заказ
блюдо «подпрыгивает» счётчиком, итог в нижней панели слегка оживает, смена статуса подсвечивается; диалоги и
«шторки» выезжают за 200–300 мс. Если в системе включено «уменьшение движения» (`prefers-reduced-motion`),
анимации отключаются.

### 1.2. Вход и роли

Вход — существующий PIN кассы (`kassa_employees`, хеш PIN, 5 неверных попыток → блок на 15 минут, токен на устройстве).
Роль определяет интерфейс: если повар ввёл PIN на планшете официанта, его перенаправит на `/kitchen`, кассира — на `/cashier`.

| Роль | `/admin` | `/waiter` | `/cashier` | `/kitchen` | `/kassa/` |
|---|:-:|:-:|:-:|:-:|:-:|
| Владелец (`owner`, общий для всех ресторанов) | ✓ | ✓ | ✓ | ✓ | ✓ |
| Администратор (`admin`) | ✓ | ✓ | ✓ | ✓ | ✓ (как продавец) |
| Официант (`waiter`) | — | ✓ | — | — | — |
| Кассир (`cashier`) | — | — | ✓ | — | — |
| Повар (`cook`) | — | — | — | ✓ | — |
| Продавец (`seller`) | — | — | — | — | ✓ |

Проверку делает middleware `kassa.app:{admin|waiter|cashier|kitchen|kassa}` (`app/Http/Middleware/EnsureKassaApp.php`,
таблица — `app/Support/Restaurant/Apps.php`). Ответ 403 содержит `home` — адрес «своего» интерфейса.
Официанта, кассира и повара нет на экране входа кассы, и войти в кассу они не могут. Кассира заводит администратор:
Сотрудники → «+ Сотрудник» → роль «Кассир — /cashier».

### 1.3. Заказ: статусы и отправки на кухню

```
официант или кассир: «Отправить на кухню» → new ─ «Готовится» → cooking ─ «Готово» → ready ─ «Подано» → served ─ «Оплата» → paid
                                                (отметки ставят официант, кассир или админка;              (продажа кассы)
                                                 экран кухни только показывает)
навынос (кассир): new → cooking → ready ─ «Выдан» ─┬─ оплачен заранее → paid (закрыт)
                  оплата — в любой момент          └─ не оплачен → served («выдан, ждёт оплаты») ─ «Оплата» → paid
отмена (до оплаты) → cancelled
```

- **Экран кухни только показывает заказы** — кнопок на нём нет. Переходы «готовится», «готово», «подано / выдано»
  ставят официант (в заказе: кнопка следующего шага у каждой отправки на кухню и статус каждой позиции), кассир (так же,
  плюс «Выдан» у навынос) и администратор (карточка заказа в админке). Отдельную позицию можно вернуть назад
  («готово» → «готовится»), поданную — нет. Запрос — `POST /{waiter|cashier|admin}/orders/{id}/status`.
- `restaurant_orders` — заказ: тип (`table` — столик, `takeaway` — навынос), номер (своя нумерация ресторана), столик,
  официант или кассир, гости, комментарий, статус, сумма, оплата, ссылка на продажу кассы. Статус открытого заказа
  пересчитывается по позициям.
- `restaurant_kitchen_tickets` — **отправка на кухню**: 1 — сам заказ, 2, 3… — дозаказы. Кухня получает отдельный чек и
  отдельную карточку на каждую отправку, поэтому дозаказ печатается только с новыми позициями.
- `restaurant_order_items` — позиции: блюдо × количество, комментарий («без лука»), цена на момент заказа и статус
  `new → cooking → ready → served` или `cancelled`.
- Повторная отправка с устройства (пропал ответ, двойное нажатие) не создаёт второй заказ: `client_uuid` отправки уникален.
- На столике может быть только один открытый заказ; вторая попытка его открыть — 409 с номером открытого заказа.
- Официант отменяет позицию, пока кухня её не начала; начатую или поданную — администратор. Кухня получает чек «ОТМЕНА».
- Заказ столика оплатить можно, когда ничего не готовится (иначе подсказка, что ждать или отменить); готовое при оплате
  считается поданным. Оплата наличными считает сдачу.
- **Навынос можно оплатить заранее**, пока блюда готовятся: продажа кассы создаётся сразу, заказ закрывается при «Выдан».
  Оплаченный заказ больше не меняется: дозаказ и отмена закрыты (возврат денег — в «Кассе и складе» у администратора).
- **Оплаченный заказ попадает в продажи кассы** (`kassa_sales`, позиции — блюда), поэтому виден в отчётах и журнале кассы
  и уходит на онлайн-сервер. Себестоимость блюд не ведётся (см. ограничения).

Вся логика — `app/Services/Restaurant/OrderService.php`. Каждая операция — одна транзакция с блокировкой строки ресторана:
официанты, кассир и админка меняют данные строго по очереди.

### 1.4. Экран кухни — пассивный настенный дисплей

Монитор кухни висит на стене, его никто не трогает: на экране нет ни одной кнопки, только заказы.

- **Колонки** «Новые → Готовятся → Готово», в заголовке — цветная точка статуса и число карточек.
- **Карточка** — одна отправка на кухню (заказ или «Дозаказ»): крупный номер, «Стол 5» или «Навынос», состав
  (количество × блюдо, комментарии повару под блюдом, отменённое зачёркнуто), комментарий к заказу и прошедшее время.
- **Просрочка** сверх норматива приготовления (админка → Настройки → норматив, по умолчанию 15 минут) — вся карточка
  мягко краснеет, таймер — красная плашка с медленной пульсацией; на 70 % норматива таймер становится янтарным.
- **Тема светлая**: белый фон, много воздуха, тонкие разделители, крупная типографика (номер 36 px, блюда 27 px на
  мониторе 1920×1080 — читается с 2–3 метров); цвет — только у статусов и просрочки. Когда заказов много, карточки
  становятся компактнее, чтобы колонка помещалась без прокрутки.
- **В шапке**: название ресторана, стоп-лист (только просмотр — ведёт админка), сообщения об отменах и проблемах
  принтера, часы.
- **Печать из браузера** идёт сама, без кнопок (см. 4.2). Повторить кухонный чек можно из заказа у официанта или
  кассира (кнопка ⎙ у отправки) и в админке («Чек на кухню»).
- **Звук нового заказа** — если браузер разрешил звук: в Chrome на кухне добавьте флаг
  `--autoplay-policy=no-user-gesture-required` (или один раз коснитесь экрана после запуска).
- **Выйти** под другим сотрудником: откройте `/kitchen?logout` — появится вход по PIN.

### 1.5. Экран кухни: опрос каждые 5 секунд, а не SSE

Доска обновляется опросом `GET /api/restaurant/kitchen/board` раз в 5 секунд (`config/restaurant.php`, `poll_seconds`).
SSE не выбран сознательно:

- **PHP держит процесс на каждое SSE-соединение.** На компьютере ресторана пул PHP-FPM — 5–10 процессов; несколько экранов
  кухни и планшетов официантов с открытым SSE заняли бы его целиком, и обычные запросы (отправка заказа, оплата) ждали бы.
  Встроенный `php artisan serve` однопоточный — одно SSE-соединение остановило бы весь сервер.
- **Опрос сам восстанавливается** после обрыва Wi-Fi, перезапуска сервера и сна планшета; ему не нужны настройки nginx
  (`proxy_buffering off`, таймауты) и keep-alive.
- **Нагрузка мала:** один лёгкий запрос раз в 5 секунд с экрана — для SQLite и 3–5 экранов это меньше 1 запроса в секунду.
- **Задержка до 5 секунд** незаметна для кухни, где норматив считается в минутах. Звук нового заказа (WebAudio, без файлов)
  звучит на ближайшем опросе. Когда экран свёрнут, опрос реже.

Таймер карточки считается от времени отправки по часам сервера (поправка на часы устройства). Он желтеет на 70 % норматива
и краснеет, когда норматив превышен. Норматив — в админке (по умолчанию 15 минут).

### 1.6. Официант на телефоне

Приложение официанта рассчитано на современный телефон: ориентир — 402 CSS-px (iPhone 17, 402×874), массовый диапазон —
390–430 px. На экране набора заказа поиск и лента категорий закреплены под шапкой, блюда — сеткой в две колонки
(название в две строки, цена и «+»), счётчик на плитке показывает, сколько уже в заказе. Итог и «Отправить на кухню» всегда
в нижней панели; нажатие на итог открывает заказ «шторкой» снизу: количество, комментарии повару, гости, комментарий.
В заказе — отметки «Готовится / Готово / Подано» у каждой отправки и статус каждой позиции, внизу «+ Дозаказ», «Счёт»,
«Оплата». Планшет (от 768 px) — как раньше: меню и заказ рядом. На 360 px ничего не ломается и нет горизонтальной прокрутки,
но целевой размер — 390–430 px.

### 1.7. Кассир и заказы навынос

Кассир — то же, что официант (зал, открытые заказы, счёт, отметки статусов, оплата наличными со сдачей), плюс:

- **Навынос**: «+ Новый заказ навынос» → блюда → «Отправить на кухню» (кухонный чек и карточка с пометкой «НАВЫНОС»,
  комментарий — например, имя гостя). Сразу открывается оплата — можно принять деньги или закрыть окно и оплатить при выдаче.
- **Очередь навынос** (раздел «Навынос»): «Готово к выдаче», «Готовится», «Выдан — ждёт оплаты»; у карточки — номер,
  комментарий, состав, сумма, «оплачен / не оплачен», кнопки следующего шага, «Выдан» и «Оплата».
- **Приём оплаты**: наличные (с расчётом сдачи и быстрыми суммами) и карта. Если включён платёжный терминал, карта у кассира
  проходит только через терминал (раздел 1.8); иначе кассир отмечает карту вручную, как официант. Оплата попадает в продажи
  кассы, как оплата у официанта.

### 1.8. Платёжный терминал кассы

Интеграционный слой — `app/Services/Restaurant/Terminal/`. Настройки — админка → Настройки → «Платёжный терминал кассы»:
включён/выключен, адрес и порт терминала в локальной сети, тестовый режим.

1. Кассир → «Оплата» → «Карта» → **«Отправить на терминал»**: сумма заказа уходит на терминал (`TerminalService::start`).
2. Экран показывает ожидание; приложение раз в 1,5 с спрашивает результат (`GET /cashier/terminal/{id}`).
3. Результат: **оплачено** → заказ закрывается (продажа «карта», на экране RRN, код авторизации, маска карты);
   **отклонено** или **отмена** → заказ остаётся открытым, можно повторить картой или взять наличные. Пока гость не оплатил,
   кассир может отменить оплату. Если терминал не ответил за `RESTAURANT_TERMINAL_WAIT` секунд (180), оплата прекращается
   с ошибкой — проверьте чек терминала.
4. **Заказ закрывается только после подтверждения** терминала. Пока оплата ждёт терминал, заказ нельзя изменить, отменить
   или оплатить иначе; ручная отметка «картой» у кассира при включённом терминале закрыта (у официанта осталась, как раньше,
   для переносного терминала у столика).

Запросы к терминалу идут вне транзакций базы: официанты и кухня не ждут, пока гость вводит PIN. Все оплаты видны
в карточке заказа админки («Оплаты через терминал»), таблица `restaurant_terminal_payments`.

**Тестовый режим — эмулятор** (`EmulatorTerminal`): денег не списывает и в сеть не ходит. После «Отправить на терминал»
в окне ожидания появляются кнопки «Гость оплатил» и «Банк отказал» — так проверяются успех и отказ. Используется
для разработки, обучения и демо; в чистой установке терминал выключен и тестовый режим тоже.

**Драйверы.** Интерфейс слоя — `PaymentTerminal`: `purchase` (отправить сумму), `status` (чем закончилось), `cancel`
(отменить), `check` (проверка связи из админки). Драйвер выбирается в `.env`: `RESTAURANT_TERMINAL_DRIVER` (по умолчанию
`json`), список — `config/restaurant.php`, `terminal.drivers`. Встроенный `json` — **протокол-образец** этого слоя:
одна строка JSON по TCP на адрес и порт терминала (`purchase` / `status` / `cancel` / `ping`, описание — в
`JsonTcpTerminal.php`). Тесты гоняют его через фейковый транспорт (`FakeTerminalTransport`).

> **Честно о реальном терминале.** Протокол конкретного банковского терминала зависит от его модели и банка
> (ECR-протокол производителя, SDK или программа банка), поэтому настоящий терминал этим образцом не подключить.
> Подключение реального терминала оформляется **отдельным драйвером в этом же слое**: класс с интерфейсом
> `PaymentTerminal` (и, при необходимости, свой транспорт `TerminalTransport`) регистрируется в `terminal.drivers`
> и выбирается в `RESTAURANT_TERMINAL_DRIVER`. Интерфейс слоя, экран кассира, API и закрытие заказа при этом
> не меняются. Второй путь — небольшой шлюз рядом с терминалом, который понимает протокол-образец `json` и переводит
> его в протокол банка. Проверить связь — админка → «Проверить связь».

## 2. Установка

Требования такие же, как у кассы: PHP 8.3+ с `sqlite3`, `mbstring`, `intl`, `curl`, `xml`, `zip`, `bcmath`, nginx,
composer. База по умолчанию — один файл SQLite. Пошагово установка сервера описана в [`docs/kassa-sklad.md`](kassa-sklad.md).
Ниже — что меняется для ресторана.

Из одной ветки получаются два варианта — разница только в `.env` и в том, запускалась ли демо-команда.

### 2.1. Чистая установка

Рабочая установка без демо-данных: после `php artisan migrate --force` в базе нет ни ресторана, ни меню, ни столиков,
ни сотрудников, ни заказов.

```dotenv
APP_ENV=production
KASSA_DEMO_ENABLED=false            # так в .env.example; при APP_ENV=production демо закрыто в любом случае
KASSA_SETUP_CODE=…                  # openssl rand -hex 6 — без него мастер на рабочем сервере закрыт
DEPLOY_MODE=local
```

Первый запуск — откройте `/admin`: **мастер первой настройки** спросит код установки из `.env`, название ресторана, имя
и PIN владельца. Дальше владелец сам создаёт меню, столики и сотрудников (администраторов, официантов, кассиров, поваров),
настраивает принтер кухни и, если нужно, платёжный терминал (по умолчанию выключен).

Демо-данные в чистую установку не попадают: сидеры проекта ресторан не трогают, команды `restaurant:demo` и `kassa:demo`
при `KASSA_DEMO_ENABLED=false` или `APP_ENV=production` даже не регистрируются в artisan, а запросы «загрузить демо»
(`/api/kassa/setup` с `demo`, `/api/kassa/data/demo`) отвечают 404. Это проверяет `tests/Feature/Restaurant/CleanInstallTest.php`.

### 2.3. Локальный сервер ресторана

Ставится на компьютер в ресторане (мини-ПК с Ubuntu 24.04 или обычный ПК), подключённый к роутеру кабелем.
Дайте ему постоянный адрес (резервирование DHCP на роутере), например `192.168.1.10`.

```bash
sudo git clone -b main https://github.com/asadbek8364-oss/kassa-restaurant.git /var/www/restoran
cd /var/www/restoran
composer install --no-dev --optimize-autoloader
cp .env.example .env
php artisan key:generate --force
```

В `.env`:

```dotenv
APP_URL=https://restoran.lan          # адрес в локальной сети (см. HTTPS ниже)
DEPLOY_MODE=local
KASSA_TIMEZONE=Asia/Tashkent          # «сегодня», отчёты и время синхронизации
KASSA_SETUP_CODE=…                    # openssl rand -hex 6, понадобится один раз в мастере
RESTAURANT_SYNC_TIME=03:40            # ежедневная синхронизация (часовой пояс KASSA_TIMEZONE)
```

```bash
touch database/database.sqlite
php artisan migrate --force

sudo chown -R www-data:www-data storage bootstrap/cache database
```

nginx — `/etc/nginx/sites-available/restoran`:

```nginx

    listen 443 ssl;
    server_name restoran.lan 192.168.1.10;
    ssl_certificate     /etc/nginx/ssl/restoran.lan.pem;      # см. «HTTPS в локальной сети»
```

оплата и отчёты работают; данные уйдут на онлайн-сервер при следующей удачной синхронизации.

#### HTTPS в локальной сети

Service worker, установка PWA и запрет на сон экрана работают только по HTTPS. Варианты:

1. **Свой сертификат (рекомендуется).** На сервере: `mkcert -install && mkcert restoran.lan 192.168.1.10`, сертификаты —
   в `/etc/nginx/ssl/`. Корневой сертификат mkcert (`mkcert -CAROOT`) установите на каждый планшет: Android — Настройки →
   Безопасность → Установить сертификат (ЦС); iPhone/iPad — профиль, затем Настройки → Основные → Об этом устройстве →
   Доверие сертификатам. Имя `restoran.lan` добавьте в DNS роутера (или используйте IP).
2. **Без HTTPS** приложения тоже работают в браузере по `http://192.168.1.10/…`, но не устанавливаются как приложения
   и без связи не открываются. Для монитора кухни на компьютере это обычно не важно (Chrome в режиме киоска).

### 2.4. Онлайн-сервер

Облачный сервер с публичным доменом и настоящим HTTPS (certbot), установка — как в [`docs/kassa-sklad.md`](kassa-sklad.md)
с nginx из раздела 2.3. В `.env`:

```dotenv
APP_URL=https://restoran.example.uz
DEPLOY_MODE=online
KASSA_TIMEZONE=Asia/Tashkent
```

На онлайн-сервере работают админка и отчёты, правка меню, столиков, сотрудников и настроек. Заказы он не принимает
(официант получит «Это онлайн-сервер…»): их ведёт локальный сервер. Онлайн-сервер может обслуживать несколько ресторанов —
у каждого свой sync-токен. Владелец создаёт ресторан в админке (меню слева → «Ресторан» → «+ Новый ресторан»).

Если ресторану не нужен сервер на месте и интернет надёжный, можно работать прямо в облаке: укажите на облачном сервере
`DEPLOY_MODE=local` (это режим «рабочий сервер ресторана») и не настраивайте синхронизацию.

## 3. Синхронизация и sync-токен

### 3.1. Настройка

1. **Онлайн-админка** → Настройки → «Сервер и синхронизация» → **«Выпустить токен»**. Токен (`rs_…`) показывается один раз,
   на сервере хранится только его SHA-256. Новый токен заменяет прежний, «Отозвать» отключает синхронизацию ресторана.
2. **Локальная админка** → Настройки → «Сервер и синхронизация»: адрес онлайн-сервера (`https://…`) и токен →
   «Сохранить» → «Проверить связь» → «Синхронизировать сейчас». Токен хранится зашифрованным (`APP_KEY`).

Синхронизация запускается раз в день в `RESTAURANT_SYNC_TIME` (`php artisan restaurant:sync`), по кнопке
«Синхронизировать сейчас» и — если последняя попытка не удалась — каждый час (`restaurant:sync --retry`).

### 3.2. Что передаётся

| Направление | Что | Правило |
|---|---|---|
| Вверх (локальный → онлайн) | завершённые заказы (оплаченные и отменённые) с позициями; продажи кассы (в том числе из заказов); возвраты, приходы, инвентаризации; снимок склада (товары с остатками) | **только добавление**: запись с известным `uuid` повторно не создаётся и не перезаписывается; повтор отправки — «дубль», не ошибка |
| Вниз (онлайн → локальный) | меню (категории, блюда, цены, стоп-лист), столики, сотрудники (с хешем PIN), настройки ресторана (название, адрес, норматив, тексты чека) | **побеждает онлайн-версия** |

У записей есть `uuid` (общий для обоих серверов — `id` у серверов разные), `store_id`, `updated_at` и отметка синхронизации:
`synced_at` у заказов и справочников ресторана; у документов кассы — `cloud_synced_at` (колонка `kassa_sales.synced_at`
уже занята офлайн-чеками телефона). Пустая отметка — «ещё не принято онлайн-сервером».

Порядок одного запуска (`app/Services/Restaurant/Sync/SyncClient.php`):

1. **push** пачками по 200 документов каждого вида (`RESTAURANT_SYNC_BATCH`); принятое онлайн-сервером помечается.
   Что не принято — остаётся неотмеченным и уйдёт при следующем запуске.
2. **pull** — полный список справочников ресторана с онлайн-сервера (меню небольшое), применяется в одной транзакции.

### 3.3. Конфликты: «онлайн побеждает»

У справочников есть `version` — версия записи на онлайн-сервере (растёт при каждом изменении там).
Локальный сервер помнит версию, которую видел последней.

- Запись изменили **только в облаке** → при pull она заменяет локальную.
- Запись изменили **только в ресторане** (например, стоп-лист вечером) → правка уходит вверх и принимается, потому что
  в облаке запись с тех пор не менялась (версии совпадают).
- Запись изменили **и там, и там** → конфликт: онлайн-сервер оставляет свою версию, локальный сервер при pull получает её,
  локальная правка теряется. В журнале — «конфликты: N».
- Новые блюда, столики и сотрудники, заведённые в ресторане, создаются на онлайн-сервере; удалённые в облаке —
  удаляются (мягко) в ресторане. Настройки при первом подключении берутся с онлайн-сервера.
- Владельцы между серверами не передаются: у каждого сервера свой владелец из мастера первого запуска.

Заказы и документы вверх **никогда не перезаписываются**: онлайн-копия оплаченного заказа неизменна, даже если тот же
`uuid` придёт снова с другими данными.

### 3.4. Журнал и пометка «есть неотправленные данные»

Админка → Настройки → «Сервер и синхронизация»: режим сервера (`DEPLOY_MODE`), что ждёт отправки, журнал запусков —
время, сколько отправлено и получено, ошибки. На онлайн-сервере журнал показывает принятые запросы локального сервера.

Если последняя синхронизация не удалась или успешной не было больше 26 часов, а данные ждут отправки, на главном экране
админки локального сервера — пометка **«Есть неотправленные данные»** с причиной и кнопкой «Синхронизировать сейчас».

### 3.5. Протокол

`Authorization: Bearer <sync-токен>`, JSON, только на онлайн-сервере (на локальном — 404):

| Запрос | Что делает |
|---|---|
| `GET /api/restaurant/sync/ping` | Проверка токена: какой ресторан |
| `POST /api/restaurant/sync/push` | `format`, `master` (локальные правки справочников с `version`), `products`, `sales`, `returns`, `incomes`, `audits`, `orders`. Ответ: принятые `uuid` по видам, конфликты справочников, отклонённые с причиной |
| `GET /api/restaurant/sync/pull` | Справочники ресторана: `settings`, `categories`, `dishes`, `tables`, `staff` (с `deleted`) |

Ссылки между записями — по `uuid` (`category_uuid`, `table_uuid`, `waiter_uuid`, `sale_uuid`…). Пакет неизвестного
формата отклоняется (`format`) — обновляйте программу на обоих серверах одновременно.

## 4. Принтер кухни

В ресторане один принтер — на кухне. Он печатает **кухонный чек** в момент отправки заказа официантом (и на каждый
дозаказ — только новые позиции), чек «ОТМЕНА» и **гостевой счёт** по кнопке «Счёт».

- **Кухонный чек** (лента 80 мм): «КУХНЯ», номер заказа или «ДОЗАКАЗ К №…», столик или «НАВЫНОС» (крупно), официант
  или кассир, время отправки, позиции крупно «2 × Плов», комментарии инверсией, комментарий к заказу. **Цен и итога нет.**
- **Гостевой счёт:** название и адрес ресторана, номер, столик или «Навынос», официант или кассир, позиции с ценами, итог,
  способ оплаты и сдача.

Шаблоны — `app/Services/Restaurant/Printing/ReceiptTemplates.php`. Чек описывается строками со стилями (`Receipt`),
из одного описания строятся и байты ESC/POS (`EscPosRenderer`), и страница для печати из браузера (`common.js`).

Способ печати выбирается в админке: Настройки → «Принтер кухни».

### 4.1. Сетевой принтер ESC/POS

1. Подключите принтер к сети, узнайте его IP (обычно печатается при включении с зажатой кнопкой FEED) и закрепите адрес
   на роутере. Режим порта — RAW/JetDirect, порт **9100**.
2. В админке: «Сетевой принтер ESC/POS», IP, порт, кодовая страница, ширина строки (48 символов — 80 мм, 32 — 58 мм).
3. **«Тестовая печать»** — печатает сразу и сообщает ошибку, если принтер недоступен. На чеке — русский алфавит, крупный и
   инверсный текст. Если вместо букв непонятные символы — смените кодовую страницу: CP866 (`ESC t 17`) или
   Windows-1251 (`ESC t 46`); у некоторых моделей номера таблиц другие — сверьтесь с паспортом принтера.

Очередь (`app/Services/Restaurant/Printing/PrintQueue.php`, таблица `restaurant_print_jobs`):

- чек сохраняется в базе и печатается **после ответа официанту** — он не ждёт принтер, даже если тот выключен;
- если принтер недоступен (таймаут соединения 3 с), задание ждёт повтора: 5, 10, 20, 40 с, дальше раз в минуту.
  Повторы запускают экран кухни (при опросе) и планировщик (`restaurant:print-queue` каждую минуту);
- **порядок сохраняется:** пока первый чек ждёт принтер, следующие ждут вместе с ним;
- после 10 неудач (`RESTAURANT_PRINTER_MAX_ATTEMPTS`) задание помечается «не напечатан», очередь идёт дальше.
  Его можно повторить в админке или перепечатать кухонный чек из заказа (⎙ у отправки у официанта и кассира,
  «Чек на кухню» в карточке заказа админки);
- проблема с принтером видна на экране кухни и на главной админки.

### 4.2. Печать из браузера (запасной вариант)

Чеки печатает экран кухни: забирает задание из очереди (один экран — одно задание, второй его не получит) и вызывает
`window.print()` для страницы чека шириной 80 мм. Чтобы печать шла без диалога, запустите Chrome на кухонном
компьютере в режиме киоска:

```bash
google-chrome --kiosk --kiosk-printing https://restoran.lan/kitchen
```

Принтер по умолчанию в системе должен быть кухонным, поля — минимальные. Экран кухни печатает чеки сам, без кнопок.
Браузер не сообщает, вышла ли бумага: если чек не вышел, перепечатайте его из заказа (официант, кассир или админка).

### 4.3. Что проверено и что нет

Шаблоны, байты ESC/POS (сброс, кодовая страница, размеры шрифта, инверсия, отрезка), очередь, повторы, порядок,
отказ после N попыток и печать из браузера покрыты тестами с фейковым транспортом (`FakePrinterTransport`,
`tests/Feature/Restaurant/PrintQueueTest.php`). **Реальный принтер нужен для окончательной проверки:** кодовая страница
кириллицы, ширина строки, отрезка и поведение конкретной модели при обрыве соединения проверяются только на месте
кнопкой «Тестовая печать».

### 5.1. Демо-данные на сервере

Только для разработки и показа — отдельной командой, как демо кассы:

```bash
# в .env: KASSA_DEMO_ENABLED=true, APP_ENV не production
```

Создаёт (или пересоздаёт) «Демо-ресторан «Навруз»»: 22 блюда в 5 категориях (одно в стоп-листе), 8 столиков,

  принтера (официант и кассир — в рамке телефона 402 px), виртуальный принтер кухни, переключатели «Принтер кухни
  включён» и «Сбой связи с онлайн-сервером», сброс демо.
- **Руководство пользователя** (`demo/guide.html`) — открывается внутри лаунчера: официант, кухня, администратор,
  принтер, синхронизация, установка на устройства, вопросы и решения, со скриншотами.
- **PDF-версия** — `demo/restaurant-guide.pdf` (A4), ссылка «Скачать PDF» в лаунчере.

Приложения в демо — те же файлы, что на сервере: `php artisan restaurant:demo-site` копирует `public/restaurant/*`
и рендерит страницы из тех же Blade-layout'ов, подключая перед `common.js` эмулятор API
`demo/assets/demo-server.js`. Если на странице есть `window.RESTAURANT_DEMO`, `common.js` отправляет запросы
туда, а не на `/api/restaurant`. Эмулятор повторяет логику `app/Services/Restaurant` (статусы и отметки без кухни,
дозаказ, отмены, навынос с оплатой заранее и «Выдан», эмулятор терминала, стоп-лист, роли, оплата, отчёты, очередь
печати, синхронизация) и хранит демо-ресторан в `localStorage` — общие данные для всех вкладок, поэтому заказ
официанта сразу виден на кухне — по событию `storage`, не дожидаясь очередного опроса.

После изменений в приложениях:

```bash
php artisan restaurant:demo-site
node demo/tools/build-guide.cjs   # скриншоты guide/*.jpg и restaurant-guide.pdf (нужен Playwright с Chromium)
```

`DemoSiteTest` падает, если `demo/` отстал от `public/restaurant` и шаблонов страниц.

## 6. API приложений

Все запросы — JSON, `Authorization: Bearer <токен входа>` (кроме `options` и `login`).

| Метод и путь | Назначение |
|---|---|
| `GET /api/restaurant/options?app=` · `POST /login` · `POST /logout` · `GET /me` | Экран входа (`app`: admin, waiter, cashier, kitchen), вход по PIN (ответ: `app`, `home`, `redirect`), кто вошёл и что ему доступно |
| `GET /{floor}/state` · `GET /{floor}/menu` | Схема зала со статусами и открытыми заказами, заказы навынос с составом, флаги терминала; меню (`menu_version` — перезагрузить при смене) |
| `POST /{floor}/orders` | Открыть заказ на столик и отправить на кухню: `table_id`, `items[]` (`dish_id`, `qty`, `comment`), `comment`, `guests`, `client_uuid` |
| `POST /{floor}/orders/{id}/items` | Дозаказ — отдельная отправка на кухню |
| `POST /{floor}/orders/{id}/status` | Отметки вместо кухни: `status` (`cooking`, `ready`, `served`; позиции — и `new`), весь заказ, `ticket_id` или `item_ids[]` |
| `POST /{floor}/orders/{id}/serve` · `/tickets/{t}/reprint` · `/bill` · `/pay` · `/cancel` · `/items/{item}/cancel` | Подано, повтор кухонного чека, счёт (с печатью), оплата `cash`/`card` (+`received`), отмена |
| `POST /cashier/takeaway` · `/cashier/orders/{id}/handout` | Заказ навынос (`items`, `comment`, `client_uuid`), «Выдан» |
| `POST /cashier/orders/{id}/terminal` · `GET /cashier/terminal/{p}` · `POST …/{p}/cancel` · `POST …/{p}/emulate` | Отправить сумму на терминал, результат (ожидание/оплачено/отклонено/отмена/ошибка), отмена, имитация `approved`/`declined` в тестовом режиме |
| `GET /kitchen/board` · `POST /kitchen/print-jobs/{id}/claim` | Доска кухни (карточки, таймеры, отмены, стоп-лист, задания печати из браузера) и печать из браузера — у кухни больше ничего нет |
| `GET /admin/dashboard` · `/orders` · `/orders/{id}` · `/reports?from=&to=` | Главная (в т. ч. навынос), заказы, карточка заказа с оплатами терминала, отчёты (по дням, сотрудникам, столикам и навынос, средний чек, популярные блюда) |
| `POST /admin/orders/{id}/status` · `/handout` · `/tickets/{t}/reprint` | Отметки статусов, «Выдан», повтор кухонного чека — из админки |
| `/admin/categories`, `/admin/dishes`, `/admin/tables`, `/admin/staff` | Меню, стоп-лист, столики, сотрудники (в т. ч. кассиры) и PIN |
| `/admin/settings/*`, `/admin/print-jobs` | Параметры ресторана, принтер, тестовая печать, платёжный терминал (`PUT /settings/terminal`, `POST /settings/terminal/test`), очередь печати |
| `/admin/sync` (`PUT`, `/ping`, `/run`, `/token`) | Режим сервера, настройка и запуск синхронизации, sync-токен (онлайн) |

Пути указаны относительно `/api/restaurant`; `{floor}` — `waiter` (официант) или `cashier` (кассир): у них общие
действия зала. Формат синхронизации — версия 2 (роль кассира, тип заказа): обновляйте оба сервера одновременно.

## 8. Известные ограничения

- **Принтер.** ESC/POS проверен только фейковым транспортом; на реальном принтере проверьте кодовую страницу, ширину и отрезку.
  Печать из браузера не знает, вышла ли бумага; без `--kiosk-printing` браузер показывает диалог печати.
- **Без Wi-Fi устройство не работает.** Сервер стоит в ресторане, поэтому интернет не нужен, но планшет официанта должен
  видеть сервер. Черновик заказа хранится на планшете до отправки и не теряется, отправка повторяется без дублей.
- **PWA и service worker требуют HTTPS** — в локальной сети нужен свой сертификат (раздел 2.3).
- **Платёжный терминал.** Встроены эмулятор (тестовый режим) и драйвер-образец `json`; протокол настоящего терминала
  зависит от модели и банка, поэтому реальный терминал подключается отдельным драйвером в этом слое (раздел 1.8) — до этого
  проверено только эмулятором и фейковым транспортом. Если связь с терминалом пропала во время оплаты, проверьте чек терминала.
- **Экран кухни без кнопок:** отметки «готовится / готово / подано» ставят официант, кассир или админка — кухне нужен
  человек, который их ставит (обычно официант при выдаче блюда с раздачи). Звук нового заказа браузер может не разрешить
  без касания экрана — для киоска есть флаг Chrome (раздел 2.3).
- **Обновление экрана кухни — до 5 секунд** (опрос, см. 1.5).
- **Конфликт решается по записи целиком:** если блюдо меняли и в облаке, и в ресторане, остаётся облачная версия всех полей.
- **Онлайн-сервер видит данные ресторана с задержкой до суток** (синхронизация раз в день; есть кнопка «Синхронизировать сейчас»).
- **Склад ресторана не связан с блюдами:** техкарт нет, продажа блюда не списывает продукты; расход видно по инвентаризации.
  Себестоимость блюд не ведётся — в отчётах кассы прибыль по блюдам равна выручке. Удаление товара на локальном сервере
  не удаляет его из онлайн-копии склада.
- **Онлайн-сервер не принимает заказы.** Кухня одна, кухонных станций нет. Навынос, оплаченный заранее, уходит на
  онлайн-сервер после выдачи (заказ закрыт), его продажа — при ближайшей синхронизации.
- Отчёты считаются в часовом поясе ресторана (`KASSA_TIMEZONE`) по дате оплаты.
